# Connect and launch execution ownership

This unapproved design defines connect/launch ownership for Julia tool builders familiar with REPLy sessions and NDJSON operations. Connect retains application ownership; launch isolates the control loop in a dedicated supervisor and treats worker retirement as runtime-wide state loss.

## Context and test shape

At cc42040, serve runs inside its caller; named sessions normally use anonymous modules and trusted host-created sessions use Main. Client supports TCP; the pending first-class-client proposal adds Unix sockets. serve_mcp defaults to an in-process dispatcher. Heavy per-session clones are reserved, not implemented.

The measured finite busy-loop request timeout-ms=50 returned success after 2.49 seconds. Define tests before implementation: connect to a prepared live process and observe a host-exposed binding; disconnect and prove that process survives; launch a runtime and observe persistent state; hold a non-yielding Julia/native eval beyond its deadline while independently pinging the supervisor; verify exactly one timeout response, failure of other pending requests, old-handle rejection and no state resurrection after explicit relaunch. Every runaway test uses a separate OS process and a 30-second external watchdog.

## Review regression test shapes

These cases extend the implementation slices; they are required future regressions, not claims that tests already exist. Process tests use an external observer and a 30-second watchdog.

| Review finding | Input / trigger | Required observation |
|---|---|---|
| DRAFT-001 | After API launch, block both caller and worker with non-yielding work; ping from an independent process | Supervisor has a distinct PID; ping/timeout meet the reference p99 bound without caller scheduling |
| DRAFT-002 | Interleave startup failure, queued timeout, completion, cancellation, retirement, delayed exit and repeated close | Only declared lifecycle transitions occur; one terminal winner; no admissions after retirement; charges persist until exit |
| CORR-001 | Race timeout, manual interrupt and completion in each mode | Attached keeps zombie accounting when live; managed retirement includes runtime-lost; exactly one terminal per eval |
| CLAR-001 | Worker acknowledges receipt of cancellation but native eval remains live | Receipt does not stop the 100 ms escalation timer; only generation/request-matched confirmed cessation does |
| CLAR-002 | DNS/connect refusal, silent TCP acceptor, valid legacy describe, malformed response and valid modern describe | One connection budget covers resolution/connect/describe; silent/malformed peers fail; valid legacy metadata is unknown |
| EDGE-001 | Client stops reading output; exhaust its queue while another client pings and a worker deadline expires | Fixed byte/frame bounds hold; slow connection closes; control handling progresses; healthy client retains terminal ordering |
| EDGE-002 | Disconnect one client with unsent and submitted evals while another client uses a sibling session | Unsent work never runs; submitted work gets cancellation; unconfirmed cessation retires runtime after 100 ms and notifies the sibling |
| EDGE-003 | Kill API/MCP owner, then separately kill supervisor during non-yielding worker eval; also kill during startup | Owner EOF triggers cleanup; supervisor death triggers OS-backed direct-worker termination without worker scheduling; unrelated runtime survives |

## Goals and non-goals

Both modes are included in this change. Goal: choose execution ownership without changing the NDJSON request protocol or silently replacing application state. Preserve current defaults and namespace isolation.

Non-goals: arbitrary PID injection/debugger attachment, a security sandbox, authentication/TLS, general migration of Julia heaps, checkpoint/replay, a portable hard memory cap without an OS backend, per-session workers, heavy clone support, forced thread termination, or transparent recovery of application effects.

## Decisions

### Two ownership modes; namespace is a separate choice

Connect uses Client against an existing TCP/Unix endpoint. In-process serve is the application-owned endpoint, not an isolated worker. Bootstrap can run in application initialization, an opt-in -L file, or an existing prompt. Merely enabling a listener does not choose Main: default anonymous-module sessions stay unchanged. The host creates any trusted Main-backed session explicitly; a client cannot grant itself host trust through the new mode selector.

No supported endpoint means connect reports a bounded connection/handshake error. It does not inspect PID memory, load a package into an unrelated process, or turn failure into an implicit managed launch. REPLy must be available in the target's environment. The application owns endpoint lifetime and must remain running; a preloaded server is not a promise that synchronous non-yielding application work will service Julia tasks.

### Proposed public surface

Existing Client(host, port) remains compatible without a new mandatory handshake. Add opt-in connect_endpoint(host, port; connect_timeout_s=5) and connect_endpoint(socket_path; connect_timeout_s=5) returning Client after validated discovery. Unix construction reuses the first-class-client proposal. One monotonic budget covers name resolution, connection establishment, the describe request and its terminal; timeout closes the attempted connection. Discovery uses an ordinary describe request with a unique id, requiring a well-formed Reply response stream and matching done terminal. A valid legacy describe without new capability fields succeeds with unknown guarantees; malformed replies, EOF, missing terminal and silent acceptors fail. No separate wire handshake or worker launch is implied. Describe validation requires ops/versions objects, json in encodings-available and encoding-current=json, plus the matching done terminal; a generic done-only response is insufficient.

Client(runtime; connect_timeout_s=5) uses this checked path against the published endpoint. MCP connect uses connect_endpoint; older constructors preserve their existing behavior.

Add launch(; project, host=ip"127.0.0.1", port=0, socket_path=nothing, startup_timeout_s=30, shutdown_grace_s=5, limits=ResourceLimits(), require_memory_limit=false) -> ManagedRuntime. The project path is required and is resolved before spawning. close(runtime) stops only the owned runtime. disconnect(client) closes that connection and cancels its pending requests under the disconnect policy below. Existing explicit shutdown RPC retains its meaning: disconnect is not a substitute for shutdown.

replyc launch --project PATH [--port PORT | --socket PATH] runs the supervisor in the foreground, prints endpoint metadata once (JSON on stdout; diagnostics on stderr), and retains ownership until interrupted/stopped. Existing eval/session commands connect to that endpoint unchanged. No implicit background daemon or global startup.jl edits.

serve_mcp gains execution=:attached (unchanged default), :connect (explicit TCP/Unix endpoint), or :managed (explicit project and launch options). Configuration is chosen by the host process, not by an LLM tool argument. use_socket remains a legacy attached transport option; contradictory options fail before creating resources. Managed/connect dispatch, including lifecycle tools, goes through the selected backend rather than a separate local manager. MCP exposes runtime-lost failures through isError=true and never automatically restarts or resubmits tools.

### Supervisor and worker

API launch starts a dedicated supervisor OS process, which starts one worker OS process containing all sessions for that runtime. The caller holds ManagedRuntime and an exclusive ownership pipe to the supervisor; it does not host the deadline loop. Foreground replyc launch runs that same supervisor as its command process. MCP managed mode is an owner of a separate supervisor. Supervisor startup disables user startup files and loads only REPLy control code; its event loop uses asynchronous I/O; arbitrary user/application code stays in the caller or worker. The reference latency contract assumes runnable supervisor CPU capacity on the stated reference machine, not guaranteed real-time OS scheduling. Blocking the API caller must not block the supervisor. The supervisor retains connection framing, admission, connection-scoped request identity, deadlines and the request registry; user code, session state and execution/introspection operations stay in the worker. ping and runtime-capability/describe information are handled by the supervisor without waiting for worker evaluation. Worker/session-specific lookups go to the worker and fail explicitly when it is lost. No arbitrary Julia objects or application globals are copied into the parent.

Use Julia's existing process primitives, with no new runtime dependency mandated. Private IPC reuses bounded NDJSON on anonymous pipes. Worker protocol stdout carries frames only; ordinary user output is captured into out/err frames and worker diagnostics use stderr. Malformed/oversized IPC or EOF retires that generation rather than silently desynchronizing framing. Readers, writers and deadline handling cannot synchronously wait on a running eval. Validate resolved project, worker startup and an explicit ready handshake before publishing the endpoint. Startup timeout defaults to 30 seconds; a failure closes owned pipes/listeners and initiates worker cleanup. Caller-supplied host/port/socket combinations obey existing serve rules. Launch's startup clock begins at API entry and covers project resolution, both process starts, cleanup capability setup, memory setup and readiness. Startup, owner-control and worker IPC descriptors are exclusive, close-on-exec except for their intended inheritor, and never passed to user subprocesses. Worker stdout frames include internal runtime/generation/connection/request identity; public wire keys remain unchanged.

### Bounded transport and backpressure

Private IPC has a 16 MiB serialized frame ceiling, including framing. Larger legal public requests fail admission with done/error/request-too-large before worker submission. Output text is split at UTF-8 boundaries so each serialized frame fits; indivisible values/errors are bounded before IPC encoding. Requests whose serialized internal envelope exceeds the frame ceiling are rejected before any IPC byte is sent. This IPC limit is separate from the public max_message_size input limit. Each worker-link and each public connection has an asynchronous outbound queue bounded by 32 MiB and 128 frames, whichever fills first; one in-progress write counts toward both bounds. Each admitted request reserves one terminal slot of at most 64 KiB in a separate bounded registry; admissions stop at max_concurrent_evals + 2 * max_concurrent_evals pending evals globally. Non-eval operations reserve from a separate pool of at most eight requests per connection, with connection count governed by max_connections; overflow closes that connection rather than allocating an unbounded registry. Terminal reservation never bypasses earlier response frames on the same stream.

The deadline loop, registry lock and IPC reader never wait for a transport write. Full public output queues close only that slow connection and apply the disconnect cancellation policy. The reader keeps draining/discarding that connection's worker output so it cannot stall other clients. A worker-link writer that cannot queue or finish a frame by that request's deadline retires the generation if any bytes may have reached the worker; only requests with zero bytes submitted can time out without retirement. Terminal selection/queueing is atomic, but network delivery cannot be promised to a peer that has stopped reading. The 100 ms p99 timeout/ping observation uses continuously reading local clients; stalled clients receive connection closure instead of an unconditional delivery guarantee. Audit records distinguish terminal selected, delivered and discarded, without altering exactly-one terminal selection.

### Deadline, cancellation and loss

The supervisor starts a monotonic deadline at execution admission, including queue time, with effective timeout=min(request timeout, server max). Atomically choose completion or deadline. If the deadline wins, mark that generation unavailable before sending exactly one done/error/timeout/runtime-lost terminal to the triggering request and initiating termination; do not wait for worker reaping before serving ping or returning the terminal. Other accepted requests not already terminal receive exactly one done/error/runtime-lost response and are never submitted/replayed elsewhere. Completion observed first remains completed; late frames from a retired generation are discarded.

A deadline before a request reaches the worker cancels that queued request without destroying the worker: it has not mutated worker state. Once any byte of a timed-out request has been sent to the worker and completion is unknown, treat its state as potentially mutated and retire the whole runtime. Per-session FIFO is retained inside the worker. Managed manual interrupt first attempts cooperative cancellation. Its 100 ms timer starts when the supervisor accepts cancellation for a submitted request. A worker acknowledgement of receipt or scheduling InterruptException is insufficient: only observed cessation of that eval, matched to runtime generation, connection and request identity, stops escalation. Completion, the effective deadline and cancellation escalation share one atomic terminal decision. If cessation is observed first, preserve its completed/interrupted outcome and keep the runtime; if the effective deadline wins, emit done/error/timeout/runtime-lost; if the cancellation grace expires first, retire/terminate and select done/interrupted/runtime-lost. Other pending requests receive done/error/runtime-lost. Repeated interrupt does not reset grace. The interrupt RPC's own terminal only acknowledges the cancellation request; it does not certify the eval stopped. Native cleanup may be delayed by OS conditions; this does not delay supervisor responses.

Kill escalation covers the owned process tree where supported; after shutdown_grace_s the supervisor escalates rather than waiting indefinitely. Do not release live-worker resource accounting until actual termination is observed. A worker whose exit cannot be confirmed keeps its process/resource charge and is reported as unreaped; capacity checks can reject a relaunch. A retiring runtime reports retired until cleanup is known to be delayed; unconfirmed exit after escalation reports unreaped. Closing rejects admissions, and a closed handle reports closed; request queued/submitted/cancelling substates still report ready. No claim of real-time OS scheduling, universal kill/reaping latency or rollback is made.

Lost runtime handles remain lost; explicit launch creates a new runtime ID, generation and session UUIDs. No automatic restart or replay. Existing external writes are not undone. Shared ownership matters: terminating this worker destroys every named/ephemeral session there, while another managed runtime and connected external applications survive. Intentional close is idempotent and follows the same pending-request/cleanup ownership rules without promising rollback.

### Disconnect and abrupt owner death

An ordinary client disconnect does not close the owned runtime handle. Cancel unsent requests from that connection and remove them from admission queues; they never execute. For submitted requests request cooperative cancellation with the same 100 ms cessation grace as manual interrupt; if cessation is not confirmed, retire the entire generation. The disconnected client's selected terminal is discarded; surviving clients receive runtime-lost for their pending requests and all old sessions become unusable. Cancellation is keyed by connection identity as well as request id; another client's equal wire id must not be cancelled. A disconnect after completion preserves runtime availability. Attached disconnect retains BIZ-008 cooperative cancellation and never kills the external application.

Loss of the API/MCP owner's exclusive control pipe stops admissions and triggers owned close even when the owner dies without finally/EOF handling. Abrupt supervisor death must terminate the direct worker through an OS-backed owner-death mechanism that does not need the worker's scheduler. Managed startup fails before readiness if that mechanism is unavailable. Initial managed support targets Linux; other OSes keep connect/attached support and reject launch until an equivalent backend is implemented and tested. The Linux worker starts with --startup-file=no and installs controls before evaluating caller-selected bootstrap or request code. It must configure SIGKILL parent-death delivery, check its supervisor PID supplied at spawn against getppid after setup to close the startup race, and preserve the creating supervisor thread's lifetime. Parent-death delivery does not contain arbitrary descendants: advertise orphan-cleanup=worker and process-tree-cleanup=unsupported unless a separately tested containment/reaper backend guarantees descendant cleanup after supervisor death. Memory containment alone does not qualify as owner-death cleanup. This is trusted-local ownership, not protection against user code deliberately disabling its controls.

On graceful close/owner EOF, the live supervisor retains charges until direct worker exit and, when enforced, contained process-tree exit are confirmed. After supervisor death no live accounting service remains: OS containment supplies termination, and a dead ManagedRuntime is never reused or reported reclaimed without an external exit observation. No terminal delivery is promised after supervisor death. Forced-death tests require observed worker exit within the 30-second external watchdog on the supported test platform; this is a regression gate, not universal OS reaping latency.

### Memory and capability reporting

Extend describe with scalar mode/limit fields, retaining the existing flat response convention: execution-mode (attached or managed), timeout-enforcement (cooperative or supervised), memory-enforcement (unsupported or os), effective-memory-limit-mb (0 when unsupported), runtime-id, runtime-state, orphan-cleanup and process-tree-cleanup for managed endpoints. Existing describe clients may ignore added fields. Connected legacy endpoints lacking this metadata are classified unknown, never promoted to supervised.

max_memory_mb retains its default/configuration compatibility. Attached mode reports unsupported rather than reserving or counting per-session Julia heap memory. Managed mode applies a per-runtime process-tree OS cap when an enforceable backend is available; Julia --heap-size-hint or periodic RSS checks do not qualify as a hard cap. require_memory_limit=true must fail startup before user code if enforcement is unavailable. false permits an explicitly reported unsupported cap; no cross-platform enforcement claim is made. OS-specific backend support (for example delegated Linux cgroups) must be capability-detected and tested; without permissions it is unsupported, not silently successful. The supervisor is outside the worker's enforced memory domain.

### Compatibility and sequencing

Launch mode is additive, but narrowing attached deadline claims is a normative contract change requiring approval. Existing ordinary sessions, heavy type rejection, protocol envelopes and bootstrap behavior remain. Existing light-session cloning works inside one worker; cross-runtime cloning/state transfer is rejected as unsupported, not a best-effort deepcopy across processes. clone type heavy remains reserved. No new execution-mode key silently changes eval namespace or migration semantics.

Completed fix-eval-timeout must be adopted first; retain its quarantine/retained-accounting semantics for attached timeouts when the scheduler can deliver them. Its broad response-bound wording is superseded by the mode-aware security delta here. q8dz implements this approved boundary; it cannot be closed merely by relabeling current behavior. Review add-first-class-client, refactor-mcp-adapter and update-cli-spec in application order. Do not close nv28 until the maintainer approves this draft and successors are synchronized.

## Validation and release scope

On reference Linux hardware (openspec/project.md), warm workers then run at least 100 trials each of finite busy-loop and blocking native evals with timeout-ms=100. With continuously reading local clients and runnable supervisor CPU capacity, managed timeout observation (relative to effective deadline) and concurrent supervisor ping observation (relative to request send) must have p99 <=100 ms after the relevant trigger; each request has one terminal. Use an external observer so a stalled worker cannot stall measurements. Process exit and accounting cleanup are measured separately. Functional managed process lifecycle tests run on Linux until another owner-death backend is verified; connect/attached tests run on supported CI OSes; Unix-only tests run where Unix sockets are supported.

Memory-enforcement tests use a controllable OS backend on capable CI; unavailable backends test strict rejection and honest optional reporting. Record capabilities so a skipped OS backend is not represented as verified enforcement. Run just test, just smoke-test, openspec validate add-managed-execution-modes --strict, spk lint on this delta and ah check --changes add-managed-execution-modes after corresponding contracts exist. Cold-start latency is reported separately and bounded by configured startup timeout, not the existing 10 ms light-session creation target.

## Alternatives and risks

Cooperative-only release would preserve attached behavior but does not meet the requested managed workflow. Worker-only replacement would break access to existing applications. A reserved thread is useful for responsiveness experiments but is not the process reclamation boundary. Per-session workers improve failure isolation but add startup/resource/clone complexity; defer them in favor of an explicit runtime-wide loss contract.

The shared worker sacrifices unaffected session state on timeout; expose this before use. Project loading/compilation can exceed the default startup budget; allow explicit configuration, report startup failure, never publish an unready endpoint. Subprocesses and external effects require explicit containment capabilities; isolation is not a security sandbox. Benchmark latency depends on stated hardware/load assumptions.

## Approval and migration

This proposal selects both modes with their distinct guarantees; it remains unapproved. After approval update nv28/q8dz and xbb9/xbb9.1 acceptance to these guarantees, then implement the vertical slices in tasks.md. Rollback can remove the opt-in launch/MCP-managed entry points without changing connect defaults; it cannot restore discarded worker state. No deployment is part of this change.
